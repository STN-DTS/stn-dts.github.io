Our app has to work in both English and French, and that includes the URLs. A French user should land on
`/fr/a-propos`, not `/fr/about`. Getting this right with React Router took a bit of work, so in this post I'll walk
through how we set it up in a real project using React Router v7 and i18next (a popular translation library).

I'll cover how we define localized routes, how we link to them, how the language switcher works, and how translations
get loaded on the server during server-side rendering (SSR) and in the browser afterwards.

## What we wanted

We had three goals. Search engines should be able to find and index every language version of every page. Users should
be able to switch languages easily and share a link that opens in the right language. And developers should be able to
add new pages without fighting the routing setup.

We got there by putting the language at the start of the URL path (`/en/about`, `/fr/a-propos`) and adding a few custom
pieces on top of React Router to handle the rest.

## Defining the routes

We keep the localized routes in their own file instead of mixing them in with the rest of the route config.

`app/i18n-routes.ts` describes every localized route using a custom `I18nRoute` type:

```typescript
// app/i18n-routes.ts

export type I18nRoute = I18nLayoutRoute | I18nPageRoute;
export type I18nLayoutRoute = { file: string; children: I18nRoute[] };
export type I18nPageRoute = { id: string; file: string; paths: Record<Language, string> };

export const i18nRoutes = [
  {
    file: 'routes/layout.tsx',
    children: [
      {
        id: 'PROT-0001',
        file: 'routes/index.tsx',
        paths: { en: '/en/', fr: '/fr/' },
      },
      {
        id: 'EMPL-0001',
        file: 'routes/employee/index.tsx',
        paths: {
          en: '/en/employee',
          fr: '/fr/employe',
        },
      },
      // ... more routes
    ],
  },
] as const satisfies I18nRoute[];
```

Each page route has an ID, the file that renders it, and one path per language. Layout routes just wrap a list of child
routes, so you can nest them as deeply as you need.

Because the array is declared `as const`, we can pull types out of it. The `I18nRouteFile` and `I18nRouteId` types are
built from `i18nRoutes`, so TypeScript will complain if you reference a route file or ID that doesn't exist. Keeping these
definitions apart from the main route config also makes them easier to find and maintain.

## Turning them into React Router routes

React Router doesn't know anything about our `I18nRoute` type, so `app/routes.ts` converts it into the
`RouteConfigEntry[]` format React Router expects. The `toRouteConfigEntries` function walks the tree recursively:

```typescript
// app/routes.ts

import { layout, route } from '@react-router/dev/routes';
import { i18nRoutes, isI18nPageRoute } from './i18n-routes';

function i18nPageRoutes(i18nPageRoute: I18nPageRoute): RouteConfigEntry[] {
  return Object.entries(i18nPageRoute.paths).map(([language, path]) => {
    const id = `${i18nPageRoute.id}-${language.toUpperCase()}`;
    return route(path, i18nPageRoute.file, { id: id });
  });
}

export function toRouteConfigEntries(routes: I18nRoute[]): RouteConfigEntry[] {
  return routes.flatMap((currentRoute) => {
    return isI18nPageRoute(currentRoute)
      ? i18nPageRoutes(currentRoute)
      : layout(currentRoute.file, toRouteConfigEntries(currentRoute.children));
  });
}

export default [
  // ... other routes
  ...toRouteConfigEntries(i18nRoutes),
  // ... other routes
] satisfies RouteConfigEntry[];
```

For each page route, `i18nPageRoutes` creates one React Router route per language and gives each one a unique ID like
`EMPL-0001-EN` or `EMPL-0001-FR`. Layout routes become React Router layouts, with their children converted the same
way. The result gets spread into the default export alongside any routes that don't need translating.

## Linking with `<AppLink>`

Now that the routes exist, we need a way to link to them. Hard-coding `/en/employee` in a link would break as soon as
the user switched to French, so we wrapped React Router's `<Link>` in our own `<AppLink>` component.

`app/components/links.tsx`:

```tsx
// app/components/links.tsx

export function AppLink({
  children,
  disabled,
  hash,
  lang,
  params,
  file,
  search,
  to,
  ...props
}: AppLinkProps): JSX.Element {
  const { currentLanguage } = useLanguage();

  if (to !== undefined) {
    return (
      <Link lang={lang} to={to} {...props}>
        {children}
      </Link>
    );
  }

  const targetLanguage = lang ?? currentLanguage;

  // ... error handling

  const route = getRouteByFile(file, i18nRoutes);
  const pathname = generatePath(route.paths[targetLanguage], params);

  const langProp = targetLanguage !== currentLanguage ? targetLanguage : undefined;
  const reloadDocumentProp = props.reloadDocument ?? lang !== undefined;

  return (
    <Link lang={langProp} to={% raw %}{{{% endraw %} hash, pathname, search {% raw %}}}{% endraw %} reloadDocument={reloadDocumentProp} {...props}>
      {children}
    </Link>
  );
}
```

If you pass a regular `to` prop, `<AppLink>` behaves just like `<Link>`. The interesting case is when you pass a `file`
prop instead. That's a type-safe reference to a route file from `i18nRoutes`. The component gets the current language
from our `useLanguage` hook, looks up the route, and builds the right URL for that language.

So instead of thinking about URLs, you write this:

```tsx
<AppLink file="routes/employee/profile/personal-information.tsx">
  Personal Information
</AppLink>
```

In English, that links to `/en/employee/profile/personal-information`. In French, it links to
`/fr/employe/profil/informations-personnelles`.

## The language switcher

Every bilingual app needs a way to switch languages. Ours is a `LanguageSwitcher` component in
`app/components/language-switcher.tsx`, built from the pieces we've already seen:

```tsx
// app/components/language-switcher.tsx

export function LanguageSwitcher({ className, children, ...props }: LanguageSwitcherProps) {
  const { altLanguage } = useLanguage();
  const { search } = useLocation();
  const { file } = useRoute();
  const params = useParams();

  return (
    <InlineLink
      className={cn('text-slate-700 sm:text-lg', className)}
      file={file as I18nRouteFile}
      lang={altLanguage}
      params={params}
      reloadDocument={true}
      search={search}
      {...props}
    >
      {children}
    </InlineLink>
  );
}
```

It works like this. `useLanguage()` gives us the other language (`altLanguage`). `useRoute()` tells us which route file
is rendering the current page, so we can find its translated path in `i18nRoutes`. `useLocation()` and `useParams()`
give us the current query string and URL parameters so the user ends up on the same page with the same data.

All of that gets passed to `<InlineLink>`, which uses `<AppLink>` under the hood. We set `reloadDocument={true}` to force
a full page reload. That way the server renders the page in the new language and the browser loads the right
translations, instead of React Router trying to swap languages on the client.

Since the component figures everything out from the current page, you can drop it anywhere in the app.

## Translations on the server

During SSR, we create a fresh i18next instance for every request. If we shared one instance across requests, two users
asking for different languages at the same time could get each other's translations.

The server entry point, `app/entry.server.tsx`, works out the language from the request and sets up i18next:

```tsx
// app/entry.server.tsx

export default async function handleRequest(
  request: Request,
  responseStatusCode: number,
  responseHeaders: Headers,
  routerContext: EntryContext,
  loadContext: AppLoadContext,
) {
  const language = getLanguage(request);
  const i18n = await initI18next(language);

  // ... render the app
}
```

The server config in `app/i18n-config.server.ts` preloads every namespace (a namespace is just a group of related
translation strings) in both languages, so the server always has everything it needs:

```typescript
// app/i18n-config.server.ts

export async function initI18next(language?: Language): Promise<i18n> {
  const { I18NEXT_DEBUG: debug } = serverEnvironment;
  const i18n = createInstance().use(initReactI18next);
  const namespaces = getNamespaces(i18nResources);

  await i18n.init({
    debug: debug,
    defaultNS: false,
    fallbackLng: 'en',
    lng: language,
    preload: ['en', 'fr'],
    supportedLngs: ['en', 'fr'],
    ns: namespaces,
    resources: i18nResources,
    interpolation: { escapeValue: false },
    // ...
  });

  return i18n;
}
```

## Translations in the browser

The browser is a different story. We don't want to ship every translation string to every user on the first page load,
so the client only loads the namespaces the current route needs.

The client entry point, `app/entry.client.tsx`, looks at the route modules on the page, works out which namespaces they
use, sets up i18next, and then hydrates the app (hydration is when React takes over the HTML the server sent and makes
it interactive):

```tsx
// app/entry.client.tsx

startTransition(() => {
  const routeModules = Object.values(globalThis.__reactRouterRouteModules);
  const routes = routeModules.filter((routeModule) => routeModule !== undefined);
  void initI18next(getI18nNamespace(routes)).then(hydrateDocument);
});
```

The client config in `app/i18n-config.client.ts` uses `i18next-fetch-backend` to fetch translations from the server as
they're needed. It reads the language from the `lang` attribute on the `<html>` tag, which the server already set:

```typescript
// app/i18n-config.client.ts

export async function initI18next(namespace: Namespace): Promise<i18n> {
  const { BUILD_REVISION, I18NEXT_DEBUG } = globalThis.__appEnvironment;

  const languageDetector = {
    type: 'languageDetector',
    detect: () => document.documentElement.lang,
  } satisfies LanguageDetectorModule;

  await i18Next
    .use(languageDetector)
    .use(initReactI18next)
    .use(I18NextFetchBackend)
    .init({
      debug: I18NEXT_DEBUG,
      ns: namespace,
      fallbackLng: 'en',
      defaultNS: false,
      preload: ['en', 'fr'],
      supportedLngs: ['en', 'fr'],
      backend: { loadPath: `/api/translations?ns={{ns}}&lng={{lng}}&v=${BUILD_REVISION}` },
      interpolation: { escapeValue: false },
    });

  return i18Next;
}
```

## The `/api/translations` endpoint

The client gets its translations from `/api/translations`. It's a small API route that takes a language (`lng`) and a
namespace (`ns`) as query parameters and returns that set of translations as JSON.

```typescript
// app/routes/api/translations.ts

import type { Route } from './+types/translations';

import { serverDefaults } from '~/.server/environment';
import { HttpStatusCodes } from '~/errors/http-status-codes';
import { initI18next } from '~/i18n-config.server';

// we will aggressively cache the requested resource bundle for 1y
const CACHE_DURATION_SECS = 365 * 24 * 60 * 60;

export async function loader({ context, params, request }: Route.LoaderArgs) {
  const url = new URL(request.url);

  const language = url.searchParams.get('lng');
  const namespace = url.searchParams.get('ns');

  if (!language || !namespace) {
    return Response.json(
      { message: 'You must provide a language (lng) and namespace (ns)' },
      { status: HttpStatusCodes.BAD_REQUEST },
    );
  }

  const i18next = await initI18next();
  const resourceBundle = i18next.getResourceBundle(language, namespace);

  if (!resourceBundle) {
    return Response.json(
      { message: 'No resource bundle found for this language and namespace' },
      { status: HttpStatusCodes.NOT_FOUND },
    );
  }

  // cache if the requested revision is anything other
  // than the default build revision used during development
  const revision = url.searchParams.get('v') ?? serverDefaults.BUILD_REVISION;
  const shouldCache = revision !== serverDefaults.BUILD_REVISION;

  return Response.json(resourceBundle, {
    headers: shouldCache //
      ? { 'Cache-Control': `max-age=${CACHE_DURATION_SECS}, immutable` }
      : { 'Cache-Control': 'no-cache' },
  });
}
```

It reuses the server-side i18next setup to look up the resource bundle (i18next's name for the translations in one
namespace and language). If you leave out `lng` or `ns` you get a 400, and if no bundle matches you get a 404.

It also sets a `Cache-Control` header. When the request includes a real build revision, the response is cached for a
year. During development, when the revision is still the default, caching is turned off so you always see your latest
changes.

## Cache busting

Caching translations for a year is only safe if users still get new translations after we deploy. We handle that by
adding a version to every translation request.

Back in `app/i18n-config.client.ts`, the `loadPath` for `i18next-fetch-backend` includes a `v` query parameter set to
`BUILD_REVISION`:

```typescript
// app/i18n-config.client.ts

export async function initI18next(namespace: Namespace): Promise<i18n> {
  const { BUILD_REVISION, I18NEXT_DEBUG } = globalThis.__appEnvironment;

  // ...

  await i18Next
    // ...
    .use(I18NextFetchBackend)
    .init({
      // ...
      backend: { loadPath: `/api/translations?ns={{ns}}&lng={{lng}}&v=${BUILD_REVISION}` },
      // ...
    });

  return i18Next;
}
```

`BUILD_REVISION` is a unique ID generated at build time. It's passed to the browser through the
`globalThis.__appEnvironment` object. Every deployment gets a new `BUILD_REVISION`, which means a new URL for every
translation file. The browser has never seen that URL before, so it downloads the new translations instead of using the
old cached ones.

## What happens on a request

Here's the whole flow from start to finish:

1. A user requests a page, like `/en/employee/profile`.
2. The server gets the request and reads the language (`en`) from the URL.
3. The server creates a new i18next instance for this request, set to `en`.
4. React renders the page to a stream, with the text in English.
5. The browser receives the HTML and starts hydrating the app.
6. The client-side i18next instance starts up and reads the language from the `<html>` tag's `lang` attribute.
7. The client fetches any other translations it needs from `/api/translations`.
8. The app is now fully interactive.

## Wrapping up

This setup has scaled well for us. The route definitions live in one place and are type-checked, `<AppLink>` means
nobody has to build localized URLs by hand, and splitting the i18next config between server and client keeps page loads
light while still rendering the right language on the server.

If your project needs to support more than one language, this makes a good starting point, and you can adapt the
pieces to fit your app.
